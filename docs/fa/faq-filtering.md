## DEYROUTE با فیلترینگ چه می‌کند؟

تانل‌هایی که فقط یک روش دارند با یک تغییر در فیلترینگ از کار می‌افتند. DEYROUTE به هر تانل یک **نردبان** می‌دهد: فهرست مرتبی از روش‌های مختلف تانل‌زدن (ترنسپورت‌ها) از برنامه‌های مختلف. در هر لحظه فقط یک پله ترافیک را می‌برد و بقیه گرم و آماده‌اند. وقتی پله فعال بسته شود، Hub بعد از چند پروب متوجه می‌شود و پله بعدی را روشن می‌کند — معمولاً ظرف ۳۵ ثانیه و بدون اینکه شما کاری بکنید. این زمان با مسدودسازی‌ای اندازه‌گیری شده که سر جایش می‌ماند (سناریوی آزمایشگاهی S08). فیلتری که هر اتصال را چند ثانیه راه می‌دهد و بعد قطعش می‌کند ممکن است دیر تشخیص داده شود، یا اصلاً تشخیص داده نشود. وقتی پله اول دوباره کار کند، تانل به آن برمی‌گردد. جزئیات و زمان‌ها: [Node پشتیبان](backup-node.md).

## نردبان پیش‌فرض

| # | ترنسپورت | چرا در نردبان است | صفحه بک‌اند |
| --- | --- | --- | --- |
| 1 | `backhaul/wssmux` | TLS + WebSocket + چندتایی‌سازی (mux): شبیه HTTPS، اتصال کم، سریع | [backhaul](../backends/backhaul.md) |
| 2 | `backhaul/tcpmux` | بدون TLS ولی با mux؛ کمترین سربار، برای وقتی که اثرانگشت TLS تانل مشکل‌ساز شده | [backhaul](../backends/backhaul.md) |
| 3 | `rathole/noise` | برنامه (Rust) و پروتکل متفاوت با رمزنگاری Noise؛ اگر فیلترینگ الگوی Backhaul را شناخت، جایگزین ارزانی است | [rathole](../backends/rathole.md) |
| 4 | `frp/tcp` | برنامه سوم با الگوی ترافیکی متفاوت (روی سیم TLS است) | [frp](../backends/frp.md) |
| 5 | `xray/reality` | کاملاً شبیه یک اتصال TLS 1.3 واقعی به یک سایت فریب (decoy)؛ پنهان‌ترین گزینه بدون UDP | [xray](../backends/xray.md) |
| 6 | `hysteria2/udp` | QUIC که با مبهم‌سازی Salamander پنهان شده، روی یک پورت UDP در بازه 30000 تا 31999 (با port hopping بین 20000 تا 20999)، هیچ‌وقت 443؛ UDP لازم دارد؛ بهترین سرعت روی لینک‌های پرافت | [hysteria2](../backends/hysteria2.md) |
| 7 | `waterwall/reverse-reality` | اتصال معکوس با ظاهر Reality؛ آخرین خط دفاعی پنهان | [waterwall](../backends/waterwall.md) |
| 8 | `direct/native` | بدون هیچ پوششی؛ فقط برای اینکه سرویس نخوابد | [direct](../backends/direct.md) |

تانل‌هایی که فقط پورت UDP دارند از نردبان `udp-default` استفاده می‌کنند:
`backhaul/udp` ← `hysteria2/udp` ← `direct/native`.
پله‌هایی که پروتکل تانل را نمی‌توانند ببرند خودکار کنار گذاشته می‌شوند.
`wireguard/kernel` تا اکتبر ۲۰۲۶ پله سوم `udp-default` بود. بعد از اینکه [گزارش میدانی](#گزارش-میدانی-از-ایران-اکتبر-۲۰۲۶) WireGuard معمولی را بسته دید، از آن بیرون رفت. اگر باز هم می‌خواهید روی یک تانل از آن استفاده کنید، به تانل یک نردبان درون‌خطی بدهید:

```bash
deyroute tunnel edit games --ladder backhaul/udp,hysteria2/udp,wireguard/kernel,direct/native
```

ترنسپورت‌های اختیاری که هیچ‌وقت در نردبان پیش‌فرض نیستند: `direct/haproxy`، `wireguard/kernel` و `awg/userspace` ([wireguard](../backends/wireguard.md))، `gost/relay-wss` ([gost](../backends/gost.md))، `chisel/wss` ([chisel](../backends/chisel.md)) و روش‌های دیگر هر بک‌اند (`backhaul/ws`، `rathole/tls`، `frp/quic` و…؛ صفحه هر بک‌اند را ببینید).

در حالت Simple اصلاً نردبان را نمی‌بینید؛ داشبورد فقط نشان می‌دهد هر تانل الان روی کدام پله است. در حالت Advanced از `5) Failover` ← `2) Ladder order` ترتیب را عوض کنید.

## می‌توانم ترتیب را عوض کنم؟

بله. نردبان‌های داخلی `default` و `udp-default` قابل ویرایش نیستند (`DEY-C022`)، ولی می‌توانید نردبان خودتان را بسازید و به تانل بدهید:

```bash
deyroute ladder list
deyroute ladder show default
deyroute ladder create stealth --rungs xray/reality,waterwall/reverse-reality,backhaul/wssmux,direct/native
deyroute tunnel edit main --ladder stealth
deyroute ladder set stealth --rungs xray/reality,backhaul/wssmux,direct/native
```

یک راهنمای ساده:

| اگر… | پیشنهاد |
| --- | --- |
| سرعت از پنهان بودن مهم‌تر است | `tcpmux` را اول بگذارید |
| فیلترینگ TLS تانل را می‌شناسد | `xray/reality` را بالا بیاورید |
| UDP بین Hub و Node رد می‌شود (`UDP ok` در `deyroute node test`) | `hysteria2/udp` را دوم بگذارید و بعد با `test-ladder` امتحانش کنید: تست UDP فقط نشان می‌دهد که دیتاگرام‌های ساده رد می‌شوند |
| Node فقط سرویس‌های TCP دارد | پله‌های udp را حذف کنید |
| سرویس UDP خود Node از نوع WireGuard، OpenVPN یا QUIC است | `backhaul/udp` دیتاگرام‌های آن را همان‌طور که هستند جلو می‌برد و `direct/native` فقط یک هدر کوتاه جلویشان می‌گذارد، پس فیلتر ممکن است باز هم آن‌ها را بشناسد (تست نشده). از پله‌های `udp-default` فقط `hysteria2/udp` آن‌ها را دوباره رمزنگاری می‌کند. پله‌هایی که پورت‌های UDP را داخل یک اتصال TCP رمزنگاری‌شده می‌برند، مثل `xray/reality` (XUDP) و `rathole/noise`، هم آن‌ها را پنهان می‌کنند، ولی UDP روی TCP وقتی بسته‌ها گم شوند تأخیر بیشتری دارد: `deyroute ladder create udp-stealth --rungs hysteria2/udp,xray/reality,backhaul/udp,direct/native` |
| روی Hub بدون دامنه، پله‌های ۱ و ۴ وصل می‌شوند و بعد قطع می‌شوند | `deyroute ladder create no-sni --rungs rathole/noise,xray/reality,waterwall/reverse-reality,backhaul/tcpmux,direct/native` (نه مثال `stealth` بالا: آن `backhaul/wssmux` دارد) |

بدون `hub.domain`، TLS تانل در `backhaul/wssmux` و `frp/tcp` هیچ نام سروری (server name) ندارد، چون این دو به IP سرور Hub وصل می‌شوند. تنظیم `hub.domain` به `frp/tcp`، `gost`، `chisel` و `rathole/tls` یک نام سرور واقعی می‌دهد، ولی به `backhaul/wss` و `backhaul/wssmux` نه: این دو همیشه به IP سرور Hub وصل می‌شوند.

برای اینکه همه پله‌ها را امتحان کنید و RTT آن‌ها را مقایسه کنید: `deyroute tunnel test-ladder main`. هر پله ۲۰ ثانیه وقت دارد. پله‌ای که اولین پروبش را پاس کند روشن می‌ماند و تا تمام شدن ۲۰ ثانیه‌اش هر ۵ ثانیه (`probe_interval_s`) دوباره پروب می‌شود؛ RTT آن میانه همین پروب‌هاست. پله‌ای که پاس شود و بعد شکست بخورد با `DEY-B073` گزارش می‌شود. در تمام مدت تست تانل قطع است. برای تانلی که فقط پورت UDP دارد، تست فقط بررسی می‌کند که unitهای هر پله اجرا می‌شوند (پایین‌تر را ببینید) و همین را هم می‌گوید.

## «پله skip‌شده» یعنی چه؟

پله‌ای که الان برای **همین** تانل قابل استفاده نیست. با یک هشدار زرد از نردبان این تانل کنار گذاشته می‌شود (رویداد `rung_skipped`)، در `deyroute tunnel show main` به شکل `skipped: <reason>` دیده می‌شود و هر ۳۰ دقیقه دوباره تست می‌شود؛ اگر پاس شد برمی‌گردد (`rung_restored`). این یک هشدار است، نه خطا. دلیل‌های رایج:

- **UDP بین Hub و Node بسته است یا هنوز تست نشده** (`DEY-B007`): `hysteria2/udp`، `wireguard/kernel`، `backhaul/udp`، `frp/quic` و `frp/kcp` به UDP نیاز دارند و فقط بعد از پاس شدن تست UDP استفاده می‌شوند. این تست وقتی Node وصل می‌شود و در هر بررسی دوباره ۳۰ دقیقه‌ای اجرا می‌شود. تست تا سه دیتاگرام کوچک و ساده از Hub به یک پورت UDP روی Node (30000 تا 31999) می‌فرستد و منتظر برگشتشان (echo) می‌ماند. پاس شدن تست فقط نشان می‌دهد که دیتاگرام‌های ساده رد می‌شوند؛ فیلتری که WireGuard، OpenVPN یا QUIC را از امضای ترافیکشان می‌شناسد باز هم می‌تواند این پله‌ها را قطع کند.
- **ترنسپورت قابل استفاده نیست** (`DEY-B006`) — مثلاً `frp/wss` با نسخه FRP که در پروژه ثابت شده در دسترس نیست (صفحه [frp](../backends/frp.md))، یا `direct/haproxy` انتخاب شده ولی روی Hub برنامه `haproxy` نصب نیست.
- **ترنسپورت نمی‌تواند پروتکل تانل را ببرد** (`DEY-B010`)، مثلاً پله فقط‌TCP در تانل UDP؛ این پله‌ها بی‌صدا کنار گذاشته می‌شوند.

## تانلی که فقط پورت UDP دارد چطور بررسی می‌شود؟

Hub یک تانل را این‌طور پروب می‌کند که از داخل تانل به یکی از پورت‌های TCP آن وصل می‌شود. تانلی که فقط پورت UDP دارد چنین پورتی ندارد، پس پله‌هایش فقط از روی unitهایشان بررسی می‌شوند: پله فعال تا وقتی unit آن روی Hub و Node اجرا می‌شود سالم حساب می‌شود. اگر فیلتری ترافیکش را قطع کند ولی unitها همچنان اجرا شوند، تانل UP می‌ماند و سوییچ نمی‌کند. چنین تانلی را از راه سرویس خودتان زیر نظر بگیرید (لاگ‌های آن، کاربرانتان) و هر وقت لازم شد دستی سوییچ کنید: `deyroute tunnel switch games --transport hysteria2/udp`. `test-ladder` هم همین محدودیت را دارد و آن را می‌گوید.

## Decoy SNI

`xray/reality` و `waterwall/reverse-reality` تانل را شبیه یک اتصال TLS 1.3 به یک سایت واقعی و بی‌خطر (سایت فریب یا decoy) نشان می‌دهند. قبل از استفاده از این پله‌ها، Hub بررسی می‌کند کدام decoy با TLS 1.3 و HTTP/2 جواب می‌دهد و اولین سایتی را که جواب بدهد انتخاب می‌کند. اگر هیچ‌کدام جواب ندهد، خطای `DEY-B042` می‌گیرید.

این بررسی روی Hub و با خانواده آدرس `hub.public_ip` انجام می‌شود (اگر IPv4 باشد، با IPv4)، پس decoy باید از Hub با همان خانواده جواب بدهد. Hub اول آدرس‌های هر نام را از DNS می‌پرسد و فقط به آدرس‌های عمومی‌ای که می‌گیرد وصل می‌شود. اگر resolver آن فقط آدرس خصوصی یا رزرو برگرداند، decoy بدون هیچ اتصالی رد می‌شود و دلیلی که رویداد `DEY-B042` نشان می‌دهد این است: `resolves to a private address from the hub (…; DNS tampering?)`. در این حالت احتمالاً DNS سرور Hub دستکاری شده: decoyهای دیگری انتخاب کنید، یا Hub را به resolverی وصل کنید که دستکاری نشده باشد (`/etc/resolv.conf`؛ با `dig +short NAME` بررسی کنید).

فهرست داخلی `dl.google.com`، `www.speedtest.net` و `www.samsung.com` است و هر کدام با هر دو پله تست شده است. فقط وقتی فهرست خودتان را لازم دارید که هیچ‌کدام از دیتاسنتر Hub کار نکند. آن‌وقت سایت‌های TLS 1.3 با HTTP/2 را که آن‌جا در دسترس‌اند و در ایران فیلتر نیستند زیر `hub:` در `config.yaml` بنویسید (از `www.microsoft.com` استفاده نکنید: `xray/reality` با آن در تست نردبان رد شد):

```bash
deyroute config edit
```

```yaml
hub:
  decoy_snis: [www.example-one.com, www.example-two.com, www.example-three.com]
```

با ذخیره فایل، اعتبارسنجی و اعمال می‌شود.

## چرا DEYROUTE به TLS من دست نمی‌زند؟

سرویس شما (ws+tls، tcp+tls، Reality و…) روی Node با گواهی، SNI و path خودش اجرا می‌شود. تانل فقط بایت‌های خام هر اتصال TCP/UDP را از پورت Hub به Node می‌برد و هیچ‌وقت آن‌ها را باز یا دوباره رمزنگاری نمی‌کند. نتیجه:

- هیچ خطای TLS از طرف تانل پیش نمی‌آید و چیزی در سرویس شما عوض نمی‌شود؛
- در کانفیگ کلاینت فقط آدرس عوض می‌شود (به IP سرور ایران)؛ SNI، host، path، UUID و fingerprint همان می‌مانند؛
- Hub نمی‌تواند ببیند کاربران شما چه می‌فرستند.

بعضی ترنسپورت‌ها (مثلاً `backhaul/wssmux` و `frp/*`) خود تانل را داخل TLS می‌گذارند؛ این یک گواهی جداست که DEYROUTE برای تانل می‌سازد (حالت `auto`، وابسته به CA داخلی) و ربطی به گواهی سرویس شما ندارد. صفحه [امنیت](security.md) را ببینید.

## پنل من IP واقعی کاربران را می‌بیند؟

معمولاً نه. تقریباً در همه ترنسپورت‌ها سرویس روی Node به‌جای IP کاربر یک آدرس محلی یا آدرس سمت Hub را می‌بیند؛ `deyroute tunnel show main` عبارت `client IP masked` را نشان می‌دهد. فقط `direct/haproxy` می‌تواند IP واقعی را با PROXY protocol برساند، به شرطی که برای تانل `advanced.proxy_protocol: true` تنظیم شده باشد و سرویس شما هم PROXY protocol را بپذیرد؛ آن‌وقت `client IP preserved` نشان داده می‌شود. `direct/haproxy` هیچ پوششی ندارد، پس گزینه مقاومی در برابر فیلترینگ نیست.

## گزارش میدانی از ایران (اکتبر ۲۰۲۶)

یک گزارش فیلترینگ به تاریخ ۱۷ اکتبر ۲۰۲۶ (2026-10-17) اتصال‌هایی را از یک دیتاسنتر در ایران (Parvaz) به Hetzner در آلمان و به Google و Cloudflare اندازه گرفته است. همه اتصال‌ها از سمت ایران شروع شده بودند و فقط پروتکل‌های استاندارد VPN تست شدند. معنی آن برای DEYROUTE:

- **جهت اندازه‌گیری‌شده.** در پله‌های Forward، Hub که در ایران است به Node وصل می‌شود: `xray/reality`، `hysteria2/udp`، `wireguard/kernel`، `awg/userspace`، `direct/native` و `direct/haproxy`. این پله‌ها در همان جهتی کار می‌کنند که گزارش تست کرده. در پله‌های Reverse، Node به Hub وصل می‌شود: همه پله‌های `backhaul`، `rathole`، `frp`، `waterwall`، `gost` و `chisel`. این جهت اندازه‌گیری **نشده** است.
- **WireGuard.** WireGuard معمولی روی IPv4 (قطع بعد از حدود ۲ ثانیه) و روی IPv6 (بی‌جواب) بسته بود. تست UDP در DEYROUTE روی چنین شبکه‌ای باز هم پاس می‌شود، و تانلی که فقط پورت UDP دارد متوجه نمی‌شود که ترافیکش قطع شده (بالاتر را ببینید). به همین دلیل `wireguard/kernel` از `udp-default` بیرون رفت.
- **تست نشده.** Salamander (`hysteria2/udp`)، Reality (`xray/reality`، `waterwall/reverse-reality`) و Noise (`rathole/noise`) جزو گزارش نبودند. گزارش درباره آن‌ها چیزی نمی‌گوید.
- **IPv6.** به خاطر این گزارش Nodeها را به آدرس IPv6 سرور Hub نبرید. IPv6 بین Hub و Node پشتیبانی نمی‌شود و در این حالت فایروال Hub پله‌هایی را که در آن‌ها Node به Hub وصل می‌شود دور می‌اندازد؛ صفحه [Join](join.md#node-را-از-طریق-ipv6-وصل-نکنید) را ببینید.

## کارهایی که DEYROUTE نمی‌کند

- **فیلترینگ داخل ایران را نمی‌تواند اندازه بگیرد.** `deyroute port check` پورت را از یک Node، یعنی از اینترنت، تست می‌کند. اینکه کاربران داخل ایران به `HUB_IP:PORT` می‌رسند یا نه اندازه‌گیری نمی‌شود؛ خروجی هم همین را می‌گوید: `Note: … it does not measure filtering inside Iran.`
- **نمی‌تواند Hub را رفع فیلتر کند.** اگر IP یا پورت Hub برای کاربران فیلتر باشد، همه ترنسپورت‌ها آسیب می‌بینند. پورت دیگری امتحان کنید یا Hub را به IP جدید ببرید ([جابه‌جایی Hub](hub-move.md)).
- **نمی‌تواند بگوید چرا یک پله شکست خورد**، بیشتر از آنچه پروب می‌بیند (timeout، reset، بی‌جوابی). فقط سراغ پله‌ای می‌رود که کار کند.
- **تضمین نمی‌کند که هیچ ترنسپورتی باز بماند.** نردبان به شما زمان و انتخاب می‌دهد؛ همه نوع فیلترینگ را شکست نمی‌دهد.
- **پنل VPN نیست.** کاربر یا کانفیگ کلاینت نمی‌سازد و سرویس شما را روی Node پشتیبان کپی نمی‌کند.
- **هیچ داده‌ای به جایی نمی‌فرستد** (بدون telemetry). تنها ترافیک بیرونی: دانلود ریلیزها و باینری بک‌اندها از GitHub یا Mirror شما، و پیام تلگرام اگر خودتان روشنش کنید.

## IP سرور Node بلاک شده — حالا چه کنم؟

وقتی همه پله‌های یک Node timeout می‌شوند، احتمالاً IP آن از سمت Hub بلاک شده (`deyroute doctor` هم همین را می‌گوید). اگر Node پشتیبان داشته باشید، تانل تا حالا به آن رفته است. وگرنه به Node یک IP جدید بدهید — خودش دوباره به Hub وصل می‌شود — یا سرور دیگری را Join کنید و پشتیبان تانل کنید.
