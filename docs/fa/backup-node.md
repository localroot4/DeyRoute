# Node پشتیبان و Failover

<div dir="rtl">

[English](../en/backup-node.md) · [فهرست](index.md)

Node پشتیبان یک سرور خارج دوم برای همان تانل است. اگر Node اصلی از کار بیفتد، همان پورت‌های Hub به Node پشتیبان می‌روند و وقتی Node اصلی دوباره سالم شد، تانل به آن برمی‌گردد.

> **Backup only works if the same service runs on both nodes.**
> یعنی Node پشتیبان باید همان سرویس را با همان کاربران و تنظیمات داشته باشد (مثلاً یک Marzban node، یا کپی کانفیگ Xray). DEYROUTE فقط ترافیک را جابه‌جا می‌کند؛ کاربران VPN شما را کپی نمی‌کند.

## افزودن Node پشتیبان

۱. سرور دوم را به‌عنوان Node وصل کنید ([Join](join.md))؛ فرض کنید شناسه‌اش `nl-1` است.

۲. آن را به تانل اضافه کنید:

```bash
deyroute tunnel backup add main --node nl-1
```

در منو: `5) Failover` ← `3) Backup nodes` ← انتخاب تانل ← `1) Add backup node`.

همه پله‌های نردبان تانل روی Node پشتیبان نصب و گرم می‌شوند و بعد این را می‌بینید:

```text
backup nl-1 ready (warm)
Backup only works if the same service runs on both nodes.
```

می‌توانید هنگام ساخت تانل هم پشتیبان را بدهید:
`deyroute tunnel add --node de-1 --ports 443,2053 --name main --backup nl-1`.
ترتیب ثابت است: اولین Node اصلی است و بقیه به ترتیب اضافه شدن، پشتیبان. `deyroute tunnel show main` آن‌ها را به شکل `de-1 (primary), nl-1 (backup)` نشان می‌دهد.

حذف Node پشتیبان:

```bash
deyroute tunnel backup remove main --node nl-1
```

## Failover چطور کار می‌کند

هر تانل در هر لحظه دقیقاً یک ترنسپورت فعال روی یک Node دارد. بقیه پله‌ها — هم روی Node اصلی هم روی همه پشتیبان‌ها — **گرم** هستند: باینری نصب، کانفیگ ساخته و سرویس systemd آماده است ولی خاموش، پس حافظه‌ای مصرف نمی‌کنند. برای همین سوییچ فقط یعنی «خاموش کردن فعلی، روشن کردن بعدی».

Hub هر ۵ ثانیه ترنسپورت فعال را پروب می‌کند: به پورت تانل خودش وصل می‌شود و بررسی می‌کند که سرویس روی Node از داخل تانل جواب بدهد. با تنظیمات پیش‌فرض:

| چه می‌شود | نتیجه |
| --- | --- |
| ۱ یا ۲ پروب ناموفق پشت سر هم (یا RTT بیش از ۳ برابر میانه ۱۰ دقیقه اخیر، به مدت ۶۰ ثانیه) | `DEGRADED` (زرد)؛ هنوز چیزی عوض نمی‌شود |
| ۳ پروب ناموفق پشت سر هم (`fail_threshold`) | `SWITCHING`: کاندید بعدی روشن می‌شود |
| کاندید ظرف ۱۵ ثانیه یک پروب را پاس کند | دوباره `UP`؛ رویداد `switch_transport` یا `switch_node` |
| کاندید شکست بخورد | ۱۰ دقیقه قرنطینه می‌شود (هر بار دو برابر، تا ۱ ساعت) و کاندید بعدی امتحان می‌شود |
| همه کاندیدها شکست بخورند | `DOWN` (`DEY-F001`)؛ کل نردبان بعد از ۳۰ ثانیه از پله ۱ دوباره امتحان می‌شود و این فاصله کم‌کم تا ۵ دقیقه زیاد می‌شود |

هدف‌های تعیین‌شده در مشخصات پروژه: از لحظه‌ای که فیلترینگ ترنسپورت فعال را می‌بندد تا وقتی تانل روی پله بعدی UP است حداکثر **۳۵ ثانیه** (p95)، و قطعی محسوس برای کاربر هنگام سوییچ حداکثر **۳ ثانیه**. عددهای اندازه‌گیری‌شده، وقتی آماده شوند، در صفحه [Benchmarks](../en/benchmarks.md) می‌آیند. وقتی تانل به Node دیگری می‌رود، همه اتصال‌های کاربران قطع و دوباره برقرار می‌شوند؛ این طبیعی است.

### کاندید بعدی کدام است (policy)

| Policy | ترتیب |
| --- | --- |
| `transport_then_node` (پیش‌فرض) | اول پله‌های بعدی روی همان Node؛ وقتی همه پله‌های آن Node امتحان شد، Node بعدی از پله ۱ |
| `transport_only` | فقط پله‌های همان Node؛ هیچ‌وقت Node دیگر |
| `node_only` | همان پله روی Node بعدی (وقتی ترنسپورت خوب است و مشکل از سرور است) |

با `deyroute tunnel edit main --policy node_only` یا `5) Failover` ← `1) Policy` عوضش کنید.

### کِی تانل به Node پشتیبان می‌رود

- **همه پله‌های Node اصلی** در این دور شکست خورده‌اند (با policy `transport_then_node`).
- **Node اصلی از دست رفته**: اتصال کنترلش بیش از ۳۰ ثانیه قطع است و پروب تانل هم شکست می‌خورد. بقیه پله‌های آن Node امتحان نمی‌شوند و Node پشتیبان مستقیم از پله ۱ امتحان می‌شود.
- **سرویس روی Node خوابیده** (مثلاً Xray متوقف شده): عوض کردن ترنسپورت فایده‌ای ندارد، پس ترنسپورت عوض **نمی‌شود**؛ تانل با همان پله به Node پشتیبان می‌رود و رویداد `service_down` ثبت می‌شود. اگر Node پشتیبان نباشد، تانل با `DEY-F005` در حالت `DEGRADED` (service down) می‌ماند: سرویس را روی Node روشن کنید.

اگر فقط اتصال کنترل قطع باشد ولی تانل هنوز ترافیک را رد کند، هیچ سوییچی انجام نمی‌شود و فقط رویداد `node_offline` را می‌بینید.

## Failback: برگشت به Node اصلی

تانل همیشه به **پله ۱ روی Node اصلی** برمی‌گردد، نه به پله قبلی.

- تا وقتی تانل جای دیگری است، Hub یک نسخه آزمایشی کوچک از پله ۱ (به اسم *canary*) به سمت Node اصلی روشن نگه می‌دارد که هیچ پورت کاربری ندارد. وقتی canary ۶ پروب پشت سر هم را پاس کرد (`recover_threshold`)، تانل برمی‌گردد.
- اگر canary ساخته نشود، تانل بعد از ۳۰۰ ثانیه کار پایدار (`failback_after_s`) برمی‌گردد.
- Node اصلی باید آنلاین باشد و سرویسش جواب بدهد.
- اگر پله ۱ ظرف ۱۵ ثانیه پروب را پاس نکند، تانل فوراً به جای قبلی برمی‌گردد، رویداد `failback_failed` (`DEY-F003`) ثبت می‌شود و زمان انتظار این تانل دو برابر می‌شود (حداکثر ۲۴ ساعت؛ بعد از یک برگشت موفق به حالت اول برمی‌گردد).

## جلوگیری از نوسان

اگر در یک ساعت بیش از ۶ سوییچ خودکار انجام شود (`max_switches_per_hour`)، سوییچ خودکار متوقف می‌شود: اگر تانل UP است همان‌جا می‌ماند، وگرنه به `direct/native` می‌رود، و رویداد `flapping` ثبت می‌شود (`DEY-F002`). سوییچ دستی همیشه مجاز است و شمرده نمی‌شود.

## کنترل دستی

| دستور | منو | کار |
| --- | --- | --- |
| `deyroute tunnel switch main --transport backhaul/tcpmux` | `2) Tunnels` ← `5) Switch transport` | همین حالا به یک ترنسپورت برو |
| `deyroute tunnel switch main --node nl-1` | همان | همین حالا به Node دیگر برو |
| `deyroute tunnel reset main` | `5) Failover` ← `5) Reset to rung 1` | همین حالا به پله ۱ روی Node اصلی برگرد |
| `deyroute tunnel pause main` | `5) Failover` ← `4) Pause / resume failover` | سوییچ خودکار را متوقف کن (پروب ادامه دارد)، مثلاً هنگام تعمیرات |
| `deyroute tunnel resume main` | همان | سوییچ خودکار را دوباره روشن کن |
| `deyroute tunnel test-ladder main` | `5) Failover` ← `6) Test ladder` | همه پله‌ها را هر کدام ۲۰ ثانیه امتحان کن و RTT و موفقیت را گزارش بده |

`test-ladder` در تمام مدت تست تانل را قطع می‌کند (اتصال کاربران می‌افتد)، برای همین باید `yes` تایپ کنید؛ در اسکریپت `--yes` بدهید. تانل متوقف‌شده در داشبورد `PAUSED` نشان داده می‌شود تا وقتی resume کنید؛ در این مدت سوییچ دستی کار می‌کند.

## پله‌ها و وضعیتشان

`deyroute tunnel show main` همه پله‌ها را روی همه Nodeهای تانل نشان می‌دهد:

| وضعیت | معنی |
| --- | --- |
| `active` | الان ترافیک را می‌برد |
| `warm` | آماده است و در یک لحظه روشن می‌شود |
| `skipped: <reason>` | فعلاً برای این تانل قابل استفاده نیست (مثلاً UDP بسته است)؛ هر ۳۰ دقیقه دوباره تست می‌شود |
| `quarantined until <time>` | به‌تازگی شکست خورده؛ تا آن زمان دوباره امتحان نمی‌شود |
| `not rendered` | هنوز روی آن Node آماده نشده |

## آستانه‌ها (حالت Advanced)

در حالت Advanced از `5) Failover` ← `7) Thresholds *` برای هر تانل این‌ها را عوض کنید:

| تنظیم | پیش‌فرض |
| --- | --- |
| فاصله پروب (ثانیه) — `probe_interval_s` | 5 |
| مهلت پروب (ثانیه) — `probe_timeout_s` | 3 |
| تعداد پروب ناموفق تا سوییچ — `fail_threshold` | 3 |
| تعداد پروب موفق برای سالم شدن — `recover_threshold` | 6 |
| برگشت به پله ۱ — `failback` | بله |
| برگشت بعد از (ثانیه) — `failback_after_s` | 300 |
| حداکثر سوییچ خودکار در ساعت — `max_switches_per_hour` | 6 |
| قرنطینه ترنسپورت شکست‌خورده (ثانیه) — `quarantine_s` | 600 |

همین کلیدها زیر `failover:` هر تانل در `config.yaml` هستند (`deyroute config edit`).

## رویدادهایی که ارزش دیدن دارند

```bash
deyroute events --tunnel main --since 24h
```

`switch_transport`، `switch_node`، `failback`، `failback_failed`، `flapping`، `service_down`، `node_offline`، `node_online`، `tunnel_down`، `tunnel_up`، `rung_skipped`. اگر تلگرام را فعال کنید (`9) Notifications`) برای هر رویداد یک پیام می‌گیرید.
